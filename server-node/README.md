# Приём заказов и кабинет Екатерины в Telegram

Node.js24, стандартные модули (включая SQLite), дополнительных runtime-зависимостей нет. Этот код сам не создаёт бота и не меняет кампании Директа. Токены и рабочие клиентские данные не должны попадать в Git, frontend, командные аргументы, отчёты или журналы HTTP.

## Контракт сайта

`POST /api/order-request`, JSON до16KiB. Точный Origin `https://shariku.ru`/`https://www.shariku.ru`, без cookies. Дополнительные origins только через закрытую настройку `SHARIKU_ALLOWED_ORIGINS`.

Поля: `requestId`UUIDv4, `phone`, `service` (`balloons`, `flowers`, `decoration`, `other`), `details`5–1000символов, `consent:true`, `consentVersion:"2026-11-07"`; необязательные `name`до80, `eventDate`YYYY-MM-DD; `website`пустой honeypot; `analyticsConsent`boolean, `clientId`/`yclid`только при разрешении аналитики. При отказе аналитические идентификаторы сервер удаляет.

Успех: HTTP200 `{ok:true,delivered:true,requestId}`, только после подтверждённого TelegramAPI и записи квитанции. Повтор того же тела/ID возвращает `duplicate:true` и не отправляет сообщение снова. Разный payload с тем жеID —409`REQUEST_CONFLICT`. Таймаут Telegram сохраняет `uncertain`, возвращает503`DELIVERY_UNCONFIRMED` и блокирует автоматическую повторную отправку: внешнийAPI не гарантирует ровноодну доставку. Не генерировать новыйID после неопределённой сетевой ошибки. Подтверждённый отказ Telegram позволяет повтор тем жеID с лимитами. Другие коды:400`INVALID_REQUEST`,403`ORIGIN_DENIED`/`TEST_DENIED`,415`INVALID_CONTENT_TYPE`,429`RATE_LIMITED`,503`NOT_CONNECTED`/`DELIVERY_UNAVAILABLE`.

Никакого события «продажа» сайт после отправки формы не вызывает.

## Telegram

Webhook `POST /api/telegram/webhook`, закрытый заголовок TelegramSecret. `allowed_updates` обязательно `message` и `callback_query`. Получатель привязывается только командой `/start TOKEN` из privatechat, при совпадении отправителя с `SHARIKU_MANAGER_USER_ID`, неистёкшем одноразовомtoken и отсутствии предыдущей привязки. Токен ссылки нужно передать только Екатерине по согласованному каналу. Привязка к произвольному человеку по обычномуStart невозможна.

Каждый заказ приходит с кнопкой «Заказ оплачен». Кабинет запрашивает полную полученную сумму, затем отдельное подтверждение. Лишь после подтверждения сохраняются сумма, время и менеджер оплаты. Предоплату не отмечают как полную оплату. Другие пользователи, групповые чаты, устаревшие подтверждения и повторные нажатия не меняют оплату. `/orders` показывает последние20заказов; `/cancel` отменяет ввод суммы. Подтверждение оплаты ещё не доказывает, что Яндекс импортировал запись или списал рекламную оплату.

## Экспорт для Центра конверсий

`GET /integrations/direct/<SHARIKU_FEED_TOKEN>/sales.csv` — закрытая секретная ссылка для настройки источника в Директе. ЭтотURL не показывать клиентам, не отправлять в аналитику и не записывать в accesslogs. На reverseproxy отключить logging всего `/integrations/direct/`. HTTPS обязателен. Секрет не хранится в исходниках. Сервер возвращает `Last-Modified`, отражающий создание/оплату экспортируемых заказов.

UTF-8, разделитель`;`, поля `id;create_date_time;client_uniq_id;client_ids;order_status;revenue`. IDзаказа и времясоздания неизменны. Формат времени `yyyy-MM-dd HH:mm:ss` в **фактическом timezone счётчика**, заданном `SHARIKU_METRIKA_TIMEZONE`. Нельзя автоматически подставлять timezone студии. `client_uniq_id` — стабильный SHA256отClientID; телефон, имя и текст заказа не экспортируются. Заказ сначала передаётся с явным `IN_PROGRESS`, после оплаты с `PAID` или согласованной целью `SHARIKU_PAID_GOAL` (например`shariku_order_paid`) и суммой врублях. Пустого статуса не бывает. Платной вДиректе должна быть **только цель оплаты**.

Технические тесты, неподтверждённая доставка, отсутствиеClientID или согласия исключают заказ из CSV. Одинyclid недостаточен для этого формата Центра: хранится для возможной отдельной интеграции, но вэтотfeed не попадает. Доступностьfeed не доказывает импорт/привязку вЯндексе. Центр загружает данные с задержкой; проверить источник и реальную привязку нужно отдельно. Создание/обновлениеCSV не является разрешением увеличивать бюджет.

## Развёртывание

Задать приватное окружение службы, не создавать реальные.env в checkout:

- `SHARIKU_SQLITE_PATH`: постоянный файлSQLite внеwebroot, каталог0700/файл0600, отдельные резервные копии.
- `SHARIKU_MANAGER_USER_ID`: проверенныйIDЕкатерины, совпадающий с еёprivateStart.
- `SHARIKU_TELEGRAM_BOT_TOKEN`: токен уже созданного бота.
- `SHARIKU_TELEGRAM_WEBHOOK_SECRET`, `SHARIKU_ORDER_HMAC_SECRET`, `SHARIKU_FEED_TOKEN`: отдельные случайные секреты минимум32ASCIIсимвола. ДляTelegramSecret использовать разрешённыеURLsafeсимволы.
- `SHARIKU_TELEGRAM_BIND_TOKEN`: отдельныйURLsafeтокен32–64символа.
- `SHARIKU_TELEGRAM_BIND_EXPIRES_AT`: ISOtimestamp, срокактивации.
- `SHARIKU_METRIKA_TIMEZONE`: timezoneсчётчика после проверки.
- `SHARIKU_PAID_GOAL`: `PAID`поумолчанию либо точныйидентификатор созданной цели оплаты.
- `SHARIKU_ORDER_TEST_SECRET`: отдельныйсерверныйсекрет для технических тестов.
- `SHARIKU_RECEIVER_URL`: точныйHTTPSorigin для административныхhelper.
- `HOST`поумолчанию127.0.0.1; `PORT`3001. `SHARIKU_TRUSTED_PROXY_ADDRESSES` — только проверенные точныеIPпрокси, передающегоX-Real-IP. ДругиеIPзаголовки не принимаются.

```sh
node server-node/migrate.mjs
node server-node/start.mjs
# После проверкиHTTPS, в том же приватном окружении:
node server-node/configure-webhook.mjs
node server-node/status.mjs
node server-node/send-secured-test.mjs
```

Последнийhelper посылает **реальное** помеченное тестовое сообщение только при ручномзапуске; оно навсегда исключено из рекламногоfeed. Сохранить напечатанныйUUID и повторять при необходимости с темже `SHARIKU_TEST_REQUEST_ID`, не создаваядубликатов. Для сквозной проверки кнопок Екатерина отмечает тестоплаченным; `status.mjs` с темжеID показывает, что оплата сохранена, а`inFeed:false`. Это техническийтест, не реальнаяпродажа и не основание расхода.

`/health` отдаёт только `{ok,ready}`, без личныхданных илисекретов. База хранит контакты/детали, доставку, аналитическиесогласия и платежныеотметки до120дней. Фоноваяочистка запускается раз вчас; SQLiteрезервныекопии требуют отдельной политикисроков. Нет публичного списка/чтения заказов. HTTPне логирует тела/URL/токены. Согласия, сведения обоператоре и фактические каналыобработки должны соответствовать действующейсхеме.
